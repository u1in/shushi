# @u1in/shushi：网格架构与子包关系

> 版本：V2.4
> 适用范围：项目级的计算器、布局引擎、行列网格、渲染器与规则文档约定

## 1. 项目目标

本项目用于展示加法、减法、乘法、除法和短除法的计算过程与竖式。每种运算均复用通用行列网格和渲染器，但保留独立的计算规则与布局规则。

## 2. 统一分层

```text
表达式 API shushi ─→ 表达式解析器 ─→ ShushiRequest ─→ shushiCore ─┐
结构化请求 shushiCore ──────────────────────────────────────────┤
分层计算器 compute* ─→ Computation ─→ 布局器 ────────────────────┼→ 宏源码
人工宏源码 / 外部宏源码 ──────────────────────────────────────────┘
        ↓
parseMacro → Macro AST → compileMacroAst
        ↓
GridScene（grid）
        ↓
SVG string renderer（SSR） / SVG DOM renderer / DOM + CSS renderer
```

- **计算层**：验证输入，执行运算，输出可检查的过程数据与语义 token。禁止输出像素、DOM、CSS、宏 AST、宏字符串或渲染器专属数据。
- **宏源码生成层（`layout`）**：联合计算结果与展示设置，使用公开宏命令填写一份可编辑的宏字符串；它不得直接构造 `GridScene`。商、进位、借位、部分被减数、部分减数、部分积等都必须降级为人类也能输入的宏命令。
- **入口与门户层**：`shushi(expression, options)` 只负责把表达式交给表达式解析器，转换为 `ShushiRequest` 后调用 `shushiCore(request)`；也可以直接调用 `shushiCore`，或绕过门户使用 `compute*` 与布局 API。
- **宏编译层**：门户 API 和分层布局器生成的宏字符串、以及人工/外部输入的宏字符串，都经过同一条 `parseMacro → Macro AST → compileMacroAst` 链路才可生成 `GridScene`。`compileMacro` 是源码级便捷入口，内部串联宏解析和 AST 编译；`createMacroAstInspection` 在这条链路旁维护 AST 节点与网格图元的回溯关系，不改变 `GridScene` 契约。
- **宏源码形式层**：`completeMacro` 将语法糖展开为显式 `GRID` / `ROW` / `CELL` / `MM` 结构，`minifyMacro` 则省略默认配置并降级为可用的最短写法；`formatMacro` 与 `unformatMacro` 只负责换行缩进和空白。它们都不执行运算，也不直接生成 `GridScene`。
- **宏 AST 检查层**：`createMacroAstInspection` 在宏编译层外维护“`GridElement.id` → AST 节点”的映射，供点击检查、单项文本编辑和删除线回退使用；`removeElementStrike` 会移除 `STRIKE`，并把 `STRIKEDOT` 改为 `DOT`。映射不写入 `GridScene`，通用网格和渲染器仍不依赖宏语法。
- **通用网格层**：用可变尺寸轨道和 `GridElement` 描述行列结构与预定义位置，不理解具体运算；该层是布局引擎与渲染器共同使用的网格核心。
- **渲染层**：SVG 字符串、SVG DOM 与 DOM/CSS 只根据 `GridScene` 画出轨道、文本、边框、圆角、删除线与调试网格；三种输出共享同一棵无 DOM SVG 渲染树，不互相解析结果。
- **渲染器样式层**：`@u1in/shushi-renderers/style.css` 是 DOM/SVG 的公共基础样式，负责图元定位基线、字体、线条和内置语义 token 的默认色板；它不包含首页或 VuePress 的页面布局。

## 3. `GridScene` 契约

`GridScene` 包含：

- `columns` / `rows`：以单位宽高定义的可变轨道；每个尺寸必须为正有限数，只描述真实可见的行列；
- `padding`、`unitWidth`、`unitHeight`、`fontSize`：场景尺寸与默认字体配置；
- `elements`：可带文本、直线、圆角或删除线的绘制元素；位置可为单元区域、行列交点、单元格边或边中点，文本可选 `fontSizeRatio`、`fontFamily` 与跨 DOM/SVG 共用的 `color` 覆盖值。一个有面积的文本单元格会划分为 3×3 九区：`LT`/`MT`/`RT` 使用上排，`ML`/`MM`/`MR` 使用中排，`LB`/`MB`/`RB` 使用下排；核心数字放在 `MM` 中心区，`MTD` 进入上中区，进位 `RB` 进入下右区。DOM 与 SVG 复用同一解析结果。直线、圆角和删除线均可选通用 `color` 与正数 `thickness` 覆盖值；删除线以单元格内的两个比例端点表达，因而不依附于文字装饰；
- `textHorizontalAlign` / `textVerticalAlign`：场景级全局文本对齐；
- `showGuideGrid`：全轨道辅助网格；
- `ariaLabel`：场景级无障碍说明。

文本单元格可以在 `content.horizontalAlign` / `content.verticalAlign` / `content.fontFamily` 提供局部覆盖值。字体解析优先级为：**单元格字体 → 场景 `fontFamily` → 渲染器基础样式**；对齐解析优先级为：**单元格覆盖 → 场景全局配置 → 渲染器基础样式**。

### 3.1 可见文本行 API（OCR 对照）

`@u1in/shushi-grid` 公开 `extractVisibleTextRows(scene: GridScene): string[]`。它只读取布局层已生成的 `GridScene`，按实际绘制锚点从上到下、从左到右合并所有非空 `text` 元素；直线、厂字弯和空白轨道不会出现在结果中。

```ts
const rows = extractVisibleTextRows(scene)
// 例如带进位的 356 + 278：['356', '+278', '11', '634']
```

它特意不输出列坐标，适合 OCR 已按书写行识别、但横向位置不稳定的比对。API 与 DOM、SVG 及 SVG 字符串渲染入口共享文本锚点规则：元素级 `horizontalAlign` / `verticalAlign` 优先于场景默认值。因此普通格内数字、左右边中点文本（例如小数点）会与同一视觉行合并，而交点、上下边界及 `RB`/`MT` 等局部定位的进位、借位提示会单独形成注记行，不会与操作数或结果混在同一字符串。相同高度的文本按横向锚点排序，完全重合时保持 `elements` 声明顺序。该 API 不辨认具体运算，因而适用于所有布局器和宏生成的网格。首页只在用户点击结果标题行中的“计算可见行”按钮时调用它，并在弹窗中呈现 JSON；按钮和弹窗不参与行合并或场景生成。

### 3.2 预定义位置与元素锚定

- `GridTrack.size` 必须是正有限数，所有列轨道和行轨道都占据真实的正尺寸。轨道可使用小数单位，例如短除法以连续的 `0.5u` 列轨道表达半格阶梯；布局层可让 `cell` 通过 `columnSpan` 合并相邻轨道，作为一个 `1u` 数字单元格。几何层和三个渲染入口只解析合并后的区域，不理解“半格”所属的运算语义。
- `GridElement.position` 是可判别联合：`cell` 表示一个或多个完整单元格区域；`intersection` 表示列边界与行边界的交点；`edge` 表示完整单元格边；`edgeMidpoint` 表示该边中点。横线、竖线和小数点可以使用这些天然存在的位置，而不再伪造轨道；布局也可选择将教学进位、借位附着在 `cell` 的既有定位宏上。宏语言的 `RBL` / `DOT` 当前降级为右侧 `edgeMidpoint` 文本；乘法进位按过程行是否紧跟横线，使用目标数字的 `RT` 或上行数字的 `RB`，并使用与普通格内文本相同的行框对齐。
- 文本按“位置矩形 / 点 + 自然尺寸盒”放置：有面积的单元格按 3×3 九区计算锚点，上、下轨道各占高度的 `25%`，左、右轨道各占宽度的 `18%`，中心轨道占剩余空间；所有区域文字都绕所属区域中心绘制。边可用于边上的文本或 `line`；交点和边中点是零面积点，仍由原始对齐值决定文字延伸方向。结构图元必须显式设置局部对齐，避免受页面全局对齐控件影响。
- Web 渲染主题中的 `line` 元素使用 2px 整数像素线宽；DOM/CSS 使用无圆角矩形，SVG 使用 `butt` 线帽，避免圆角端点和半像素定位造成边缘模糊。
- 文本、直线、圆角、删除线的内容级 `color` / `thickness` 是渲染器无关的最终视觉覆盖，优先于 `styleToken` 对应的页面 CSS；删除线必须定位在 `cell`，其 `x1Ratio`、`y1Ratio`、`x2Ratio`、`y2Ratio` 相对该单元格解析，端点可略超出 `0–1` 以标记边中点的小数点。`@u1in/shushi-macro` 的 `GRID(autoColor)` 使用编译选项传入的固定语义主题，首页五种计算器生成宏源码不固化 `autoColor`，而是依赖编译器的默认开启行为，因此 DOM/CSS 与 SVG 会从同一个 `GridScene` 读取相同颜色。通用网格层不理解“进位、借位或运算符”的语义。
- 交互预览由宿主组件按 `data-grid-element-id` 同步 `grid-element--selected`；浏览器中的 SVG 与 DOM/CSS 必须同时支持悬停、选中边框和图元点击，SVG 由宿主补充选中矩形，DOM 使用 `outline`，两者都不使用选中阴影；DOM 的线图层在交互模式下需要恢复鼠标事件。SSR SVG 字符串不承担浏览器交互，但仍通过共享渲染树保持图元结构和坐标一致。
- 除法的 `division.bracket`（厂字弯）与 `division.bracket-top-line`（厂字横）虽然分别对应 `corner` 和 `edge` 图元，但属于同一厂字视觉部件；DOM/CSS、SVG 以及命名图谱样式必须通过同一个颜色变量渲染，不能为厂字横单独指定颜色。
- 内容墨迹必须留在网格矩形内：SVG 的 `viewBox` 和 DOM 的滚动 / 裁切祖先都会裁掉网格外的内容。需要向网格外延伸时，由排版层通过 `padding` 预留空间。
- 绘制顺序：线、圆角与删除线层始终在文本层之下；同一层内按 `elements` 数组顺序绘制。内容重叠时，后出现的元素压住先出现的元素。

布局引擎共同接收 `GridRenderSettings`（方格宽度、行高、字号比例、辅助网格、默认文本对齐和可选的 `useMinimalDecimalResult`）。该开关默认关闭，仅由加、减、乘布局在完整小数结果末尾为可省略的 `0` 附加 `STRIKE`；它不改变计算层结果或播放步数。运算专属设置不得反向进入其他运算的计算层；例如除法的厂字弯、减法线和零商步骤设置属于 `RenderSettings`，乘法的横线等宽与进位显示设置属于 `MultiplicationRenderSettings`。

`GridRenderSettings.visibleStepCount` 是可选的教学检查游标。未设置时渲染完整计算结果；设置为非负整数时，布局只截取计算器已返回的 `computation.calculationSteps` 前缀，并把该前缀投影为 `GridScene`。通用渲染器不解释步骤；主页上的每个计算器独立维护游标，并通过“开始 / 上一步 / 下一步 / 结束”反复检查，不改变计算层返回的过程数据。

### 3.3 网格文本字体

默认字体是 STIX Two Math：核心包的 `renderer.css` 内置其 `@font-face`，而 `compileMacro`、`shushi` 与 `shushiCore` 缺省时都会把它写入 `GridScene.fontFamily`。网格数字保持 `tabular-nums`，保证列宽和错位对齐。`packages/fonts/` 是首页与核心包共用的本地字体资源子包，另维护 `CMU Serif` 与 `Noto Sans Math`；要改用它们或宿主自己的字体时，导入不含内置字体的 `renderer-without-font.css`，再导入相应 `@font-face` CSS。首页预览的选择器会在字体资源确认可用后重新编译当前场景，不会在 SVG/DIV 挂载后补写样式。需要混合字体时，高级调用方可在 `GridTextContent.fontFamily` 提供单元素覆盖。

### 3.4 渲染器 CSS 发布契约

渲染器的 JavaScript 入口只负责创建节点、写入场景尺寸和计算后的坐标；公共视觉基线由独立 CSS 文件发布。面向 npm 使用者时，安装统一入口后，在浏览器入口同时导入：

```ts
import { compileMacro, renderDomGrid } from '@u1in/shushi-core'
import '@u1in/shushi-core/renderer.css'

const scene = compileMacro('3,5,6;+,[2,RB(1)],[7,RB(1)],8;LN;6,3,4;')
document.querySelector('#app')?.append(renderDomGrid(scene))
```

`renderer.css` 是默认入口，包含 `.grid-dom-stage`、`.grid-svg`、`.grid-text`、`.grid-edge`、`.grid-corner`、`.grid-guide-line` 和 `data-style-token` 的公共样式，并内置 STIX Two Math；`renderer-without-font.css` 保留同一份渲染样式但不含任何 `@font-face`，供宿主自行配置字体。`fonts.css` 注册全部内置字体，`fonts/*.css` 则只注册对应字体。它们都不包含 `@u1in/shushi-web` 首页的卡片、表单和响应式布局。应用可以在导入公共 CSS 后，通过 `--grid-text`、`--grid-rule`、`--grid-guide`、`--grid-bracket`、`--grid-font-family` 和语义 token 选择器调整渲染器基础样式；语义颜色主题应通过 JavaScript 的 `colorTheme` 传入，不能在 CSS 中重新计算图元坐标。

`renderSvgGrid` 与 `renderSvgString` 都先读取 `packages/renderers/src/svg-renderer-core.ts` 生成的无 DOM SVG 渲染树：前者把节点描述创建为浏览器 `SVGSVGElement`，后者把同一份描述序列化为 XML 字符串。这样可以保证相同 `GridScene` 的几何、图层、属性和图元顺序一致；这是一致的渲染语义，不等同于浏览器 `XMLSerializer` 结果与 SSR 字符串的字节级相同。SVG 图元会把最终的颜色、字号、统一的 `400` 字重、线宽、线帽、删除线和辅助网格属性直接写入 `style`，并在 SVG 根节点固化 `font-synthesis: none`，因此 `renderSvgString(scene)` 导出的 `.svg` 或 Base64 `img` 不依赖外部 `renderer.css` 即可保留渲染器样式。`renderSvgString(scene, { embedFont: true })` 还会把场景使用的内置字体以 Base64 `@font-face` 嵌入，默认不嵌入；开启后默认使用竖式字符子集，未知字符自动回退完整字体，也可传 `fontSubset: 'full'` 强制使用完整字体；自定义字体仍需由宿主提供。

只使用纯计算、宏编译、`extractVisibleTextRows` 或 `renderSvgString` 时不需要浏览器 DOM；SVG 字符串可以直接写入文件或编码后交给 `<img>`，不需要再把公共 CSS 注入 SVG。`renderDomGrid` 也会把文本、线条、圆角、删除线和辅助网格的最终视觉值写到每个 DOM 图元；公共 CSS 仍作为兼容性和宿主主题入口保留，但不再是还原基础预览样式的必要条件。VuePress 文档站仍通过同一入口加载样式，以便页面中的交互式 DOM/SVG 继续使用共享选择器。

## 4. 多包工作区与数据流

项目使用 npm workspaces，根包名为 `@u1in/shushi`，领域包统一采用 `@u1in/shushi-*` 命名。根目录只负责工作区编排；Vite、Vue 前端应用和对外 HTML 均位于 `packages/web/`。

| 包                         | 源码位置                    | 职责                                               | 可以依赖               |
| -------------------------- | --------------------------- | -------------------------------------------------- | ---------------------- |
| `@u1in/shushi-grid`        | `packages/grid/src/`        | `GridScene` 网格契约、轨道解析和几何工具           | 无                     |
| `@u1in/shushi-calculators` | `packages/calculators/src/` | 各运算的输入校验、算法和过程结果契约               | 无                     |
| `@u1in/shushi-layout`      | `packages/layout/src/`      | 联合计算结果与展示设置，填写可编辑的运算宏源码     | `calculators`、`macro` |
| `@u1in/shushi-macro`       | `packages/macro/src/`       | 解析人类可写宏、推导通用行列结构并生成 `GridScene` | `grid`                 |
| `@u1in/shushi-renderers`   | `packages/renderers/src/`   | 只消费 `GridScene` 的 SVG 与 DOM/CSS 渲染器        | `grid`                 |
| `@u1in/shushi-web`         | `packages/web/src/`         | 首页演示组件、Tailwind 主题与浏览器集成            | 上述四个包             |

当前架构的数据流是：

```text
人工输入 ───────→ macro
                    │  parseMacro + compileMacro
calculators          ▼
    │ 输出 OperationComputation  GridScene
    ▼                           │
layout（生成宏字符串）            ▼
    │                           grid
    └──────────────→ macro       │
    ▼
renderers
    │  输出 DOM/CSS、SVG 或 SVG 字符串
    ▼
web
```

其中 `layout` 是运算专属的**宏源码填写层**；`macro` 是唯一允许产出 `GridScene` 的公式编译层。`grid` 不负责决定除法或乘法的行列规则，只提供宏编译器和渲染器共享的网格模型与几何工具。依赖方向必须单向，不得让计算器依赖布局、宏、网格或浏览器 API，也不得让渲染器依赖运算器。

### 4.1 重要原则：自动竖式必须可由人类复刻

宏语言是竖式表现的唯一事实来源。计算器只是替用户根据 `OperationComputation` 填写宏字符串，不能拥有第二套直接组装 `GridScene` 的视觉逻辑。调用对应的 `create*MacroSource` 生成的宏源码复制到宏调试的宏源码框后，必须经相同编译路径得到相同的 `GridScene`。

当既有计算器视觉无法由当前宏命令表达时，应删除或改用可表达的宏组合；不得为了保留 API 专属效果而绕过宏编译器。新增宏命令可以扩展人类的表达能力，但其语义、文档、解析、编译和测试必须同时提供，且计算器只能使用该公开命令。

`packages/web/index.html` 是唯一的 Vite 应用壳，只挂载首页演示入口。首页布局使用 Tailwind CSS，组合宏调试、AST 元素检查器、五种运算计算器和共享的 `GridPreview`；宏语言与竖式元素命名图谱由 VuePress 文档站提供，不在 Web 包中重复维护。根目录的 `npm run dev`、`npm run build` 等脚本会先进入该包执行前端命令。

各内部包通过其 `src/index.ts` 提供公共 API。跨包代码必须使用 `@u1in/shushi-<package>` 导入，不能回退为 `../../` 跨目录深层导入。

主页由 `HomePage.vue` 组合宏调试和每种运算的 Vue 计算器组件；新增运算器应新增独立组件并在该页面组合，而不是把不同运算的响应式状态混在同一个组件中。宽屏工作区采用控制区、渲染结果区和核心实现代码区三列布局；中等宽度时核心代码区落到下一行，窄屏再收为单列。宏调试与各运算结果标题行复用 `VisibleTextRowsPanel`；可见行结果默认不显示，点击“计算可见行”按钮后才调用提取 API 并打开弹窗。第三列代码面板展示当前板块对应的 TypeScript 核心调用链，使用语法高亮并支持复制完整源码。每个计算器通过 `StepPlaybackControls` 独立维护步骤游标，使用“开始 / 上一步 / 下一步”检查过程，并通过“结束”恢复完整结果。计算器通过 `GridPreview` 在 SVG、DOM/CSS 或两者模式下渲染同一份 `GridScene`。图例名称、语义 token 和字段说明由 `@u1in/shushi-docs/gallery` 统一提供，并在 VuePress 图例页展示。

## 5. 新运算器接入清单

每新增一种运算器，至少完成：

1. 在 `@u1in/shushi-calculators` 新建计算模块，例如 `packages/calculators/src/addition.ts`，并定义 `<Operation>Computation`；
2. 在集中式文档包中新建该运算规则文档，例如 `packages/docs/technical/calculator/加法计算规则.md`；
3. 在 `@u1in/shushi-layout` 新建“计算过程 → 宏源码”模块，例如 `packages/layout/src/addition-layout.ts`，并导出 `createAdditionMacroSource`；
4. 在集中式文档包中新建或扩展中文命名的专项布局文档，例如 `packages/docs/technical/layout/加法竖式排版规则.md`；
5. 为计算规则、布局映射、异常输入和关键边界条件添加测试；
6. 只通过 `compileMacro(create<Operation>MacroSource(...))` 获得 `GridScene`，再连接既有 SVG / DOM 渲染器；
7. 如提供图谱，记录可见物件、线框边界与 JSON 字段说明。

不要为了“统一”而把不同运算的算法、过程对象或行列规则压缩为一个除法风格的数据结构。
